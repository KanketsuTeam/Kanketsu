# 🏗 使用 GraalVM 构建原生镜像

Kanketsu 的**零反射**设计，让将 CLI 应用编译为 GraalVM Native Image 原生可执行文件变得**异常简单**。本指南将以一个真实项目——**Gitetsu**（基于 Kanketsu 构建的 GitHub CLI 工具）为例，一步步带你完成配置。

---

## 📋 前置条件

- **GraalVM JDK** 17 或更高版本（下载地址：[GraalVM](https://www.graalvm.org/)）
  > *如果你的应用使用了 FFM API（Foreign Function & Memory API），则需要 JDK 25。对于未使用 FFM 的应用，JDK 25+ 同样可以正常工作。*
- **Maven** 3.9+（Gradle 也可以）
- 你的 Kanketsu 应用已编译并通过测试

---

## 🧩 Maven 配置

以下是 **Gitetsu** 用于构建原生可执行文件的完整 `pom.xml` 配置。你可以将其适配到自己的项目中。

```xml
<plugin>
    <groupId>org.graalvm.buildtools</groupId>
    <artifactId>native-maven-plugin</artifactId>
    <version>0.11.0</version>
    <extensions>true</extensions>
    <executions>
        <execution>
            <id>build-native</id>
            <goals>
                <goal>compile-no-fork</goal>
            </goals>
            <phase>package</phase>
        </execution>
    </executions>
    <configuration>
        <mainClass>com.yourcompany.yourapp.Main</mainClass>
        <buildArgs>
            <buildArg>--no-fallback</buildArg>
            <buildArg>-H:+ReportExceptionStackTraces</buildArg>
            <buildArg>--enable-native-access=ALL-UNNAMED</buildArg>
            <buildArg>--initialize-at-build-time=com.yourcompany.yourapp.CLIHolder</buildArg>
            <buildArg>--initialize-at-build-time=com.yourcompany.yourapp.MyAppLogger</buildArg>
            <buildArg>--initialize-at-build-time=io.github.kanketsuteam.kanketsu</buildArg>
        </buildArgs>
        <jvmArgs>
            <jvmArg>--enable-native-access=ALL-UNNAMED</jvmArg>
        </jvmArgs>
    </configuration>
</plugin>
```

---

## 🔧 配置项说明

| 参数 / 选项                          | 用途                                                                                                                                                 |
|--------------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------|
| `--no-fallback`                      | 强制生成**纯原生可执行文件**，禁止回退到 JVM 镜像（确保最佳启动性能）。                                                                              |
| `-H:+ReportExceptionStackTraces`     | 在原生镜像中保留完整的堆栈跟踪信息，方便调试。                                                                                                       |
| `--enable-native-access=ALL-UNNAMED` | 如果应用使用了 `java.net.http.HttpClient`（常见于 REST API 调用）或其他需要原生访问的模块，则必须开启。                                              |
| `--initialize-at-build-time=...`     | **关键配置**——强制类在**构建时**而非运行时初始化。对于持有**静态状态**的类（如预构建的命令树）至关重要。如果不加，启动性能将无法达到巅峰             |
| `<jvmArgs>`                          | 传递给运行 `native-image` 工具本身的 JVM 的参数（不是传递给应用的）。这里的 `--enable-native-access=ALL-UNNAMED` 通常用于让工具能够访问 JDK 内部类。 |

### 哪些类需要构建时初始化？

- **在静态初始化器中构建命令树的类**（如 `CLIHolder`）。
- **自定义 Logger 实现**（如 `MyAppLogger`）。
- **任何持有应用全局状态、应在构建时冻结的类**。
- **避免**初始化依赖运行时输入的类（如文件路径、用户目录、环境变量等）。

## 🏗 面向原生镜像的推荐项目结构

构建原生镜像需要特别注意**类初始化顺序**。为避免运行时出现意外，我们推荐一种特定的项目结构，将**静态设置**与**运行时逻辑**分离，确保命令树在正确的时间构建。

### 推荐目录结构

```
src/main/java/com/yourcompany/yourapp/
├── Main.java                    # 入口点（包含静态 REPL/终端设置）
├── CLIHolder.java               # 持有静态 CLI 实例（命令树在此构建）
├── Commands/                    # 命令实现
│   └──YourCommand.java
└── MyAppLogger.java             # 自定义 Logger 实现
```

### 各组件职责

| 组件 | 职责 | 原生镜像注意事项 |
|------|------|------------------|
| **`Main.java`** | 入口点：设置终端/REPL，处理参数，启动 REPL 循环。 | 应尽量简洁，避免持有重量级静态状态。 |
| **`CLIHolder.java`** | **持有静态 `CLI` 实例**——在静态初始化器中构建完整的命令树。 | **必须在构建时初始化**（`--initialize-at-build-time`）。这样命令树在构建时就已冻结，确保行为一致且启动更快。 |
| **`Commands/*.java`** | 命令逻辑（action）。每个命令是一个 `public static void execute(CommandContext ctx)` 方法，由 `CLIHolder` 引用。 | 无状态（无静态字段）→ 运行时安全。 |
| **`MyAppLogger.java`** | 自定义 Logger 实现。 | 如果持有静态状态，可能需要构建时初始化。 |

### `CLIHolder` 模式

**静态持有者模式**是构建原生镜像友好设计的关键：

```java
package com.yourcompany.yourapp;

import core.io.github.kanketsuteam.kanketsu.CLI;
import spi.io.github.kanketsuteam.kanketsu.Logger;

public class CLIHolder {
    public static Logger logger = new MyAppLogger();
    public static CLI cli = CLI.builder()
            .logger(logger)
            .command("version", "Show version", version -> version
                    .action(ctx -> logger.log("MyApp 1.0.0")))
            .command("api", "Make API requests", api -> api
                    .option("endpoint", opt -> opt
                            .shortOpt("e")
                            .hasArg(true)
                            .required(true))
                    .action(ctx -> ApiCommand.execute(ctx)))
            // ... 更多命令 ...
            .build();
}
```

### `Main.java` 入口点

`main` 方法应尽量精简——只委托给 `CLIHolder.cli`：

```java
package com.yourcompany.yourapp;

public class Main {
    public static void main(String[] args) {
        // CLI 模式：直接执行参数
        if (args.length > 0) {
            System.exit(CLIHolder.cli.execute(args));
            return;
        }

        // REPL 模式（可选，需要 kanketsu-repl 模块）
        // REPL repl = new REPL(CLIHolder.cli);
        // repl.run();
    }
}
```

### 为何此模式在原生镜像中有效

1. **命令树在构建时只构建一次**——当 `CLIHolder` 标记了 `--initialize-at-build-time` 后，整棵命令树在原生镜像生成期间就已构建完毕，而不是在应用启动时。这将启动时间缩短至 **~20 毫秒**。

2. **命令无状态**——每个命令都是一个 `static` 方法，接收 `CommandContext`。没有实例状态意味着运行时初始化不会出问题。

3. **依赖运行时的逻辑被隔离**——配置加载、HTTP 请求和文件 I/O 都发生在**命令 action 内部**，而不是在静态初始化器中。这避免了对依赖运行时环境的类进行过早初始化。

### 需要避免的反模式

| 反模式                                                           | 为什么在原生镜像中会失败                                  |
|------------------------------------------------------------------|-----------------------------------------------------------|
| 在 `main()` 中构建 CLI                                           | 命令树在运行时构建，失去了 AOT 的优势，启动速度可能变慢。 |
| 在静态初始化器中加载配置文件                                     | 构建时文件可能不存在 → 构建失败或运行时错误。             |
| 在静态初始化器中使用 `System.getenv()` 或 `System.getProperty()` | 构建时和运行时的环境可能不同 → 行为不一致。               |
| 命令类中持有大量静态状态                                         | 可能导致意外的初始化顺序问题。                            |

### 示例：正确 vs 错误

**错误**——在静态初始化器中加载配置：
```java
public class ApiCommand {
    private static String token = Config.loadToken(); 
    // ...
}
```

**正确**——在命令 action 内部加载配置：
```java
public class ApiCommand {
    public static void execute(CommandContext ctx) {
        String token = Config.loadToken();  
        // ...
    }
}
```

## 🧩 整合在一起

这种结构，配合上面的 Maven 配置，可以确保：

- **可预测的原生镜像构建**——不会因类初始化顺序而出现意外。
- **快速启动（~6 毫秒）**——命令树在镜像生成时已预构建。
- **关注点清晰分离**——CLI 定义、命令逻辑和基础设施解耦。
- **易于测试**——命令 action 只是简单的静态方法。

## 🚀 构建原生可执行文件

执行 Maven 的 package 阶段来触发原生构建：

```bash
mvn clean package
```

构建成功后，原生可执行文件会出现在 `target` 目录下，文件名与你的 artifact 名称一致。

直接运行：

```bash
./target/yourapp
```

## 🧪 测试原生镜像

你可以快速验证原生镜像是否按预期工作：

```bash
./target/yourapp --help
./target/yourapp version
```

## 📌 重要提示

### 无需反射配置文件

因为 Kanketsu **从不使用反射**，所以你**不需要**提供：
- `reflect-config.json`
- `resource-config.json`
- `jni-config.json`

这是该框架最大的优势之一——你的原生构建保持简单且易于维护。

### ⚠️ 类初始化注意事项

如果你的命令树是在静态块中构建的（如示例中的 `CLIHolder.cli`），你**必须**将该类加入 `--initialize-at-build-time`。否则，命令树运行时各构建一次，在大体量应用将会导致启动时间线性增长。

### 🧩 依赖管理

确保你的 `pom.xml` 包含正确的 Kanketsu 版本和所有必需的依赖。参考：

```xml
<dependency>
    <groupId>io.github.kanketsuteam</groupId>
    <artifactId>kanketsu-core</artifactId>
    <version>2.1.1</version>
</dependency>
<dependency>
    <groupId>io.github.kanketsuteam</groupId>
    <artifactId>kanketsu-repl</artifactId>
    <version>2.1.1</version>
</dependency>
```

## 🧩 Gradle 等效配置（参考）

如果你使用 Gradle，`graalvm-native-image-plugin` 的配置大致如下：

```gradle
graalvmNative {
    binaries {
        main {
            buildArgs.add('--no-fallback')
            buildArgs.add('-H:+ReportExceptionStackTraces')
            buildArgs.add('--enable-native-access=ALL-UNNAMED')
            buildArgs.add('--initialize-at-build-time=com.yourcompany.yourapp.CLIHolder')
            buildArgs.add('--initialize-at-build-time=com.yourcompany.yourapp.MyAppLogger')
            buildArgs.add('--initialize-at-build-time=io.github.kanketsuteam.kanketsu')
        }
    }
}
```

> **注意**：请将 `com.yourcompany.yourapp` 替换为你实际的包名。

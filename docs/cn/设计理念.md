# 🏛 设计哲学

Kanketsu 建立在一个简单的信念之上：

> **一个 CLI 框架应该是显式的、可预测的、易于理解的。**

Kanketsu 的每一个设计决策都遵循这一信念。框架不追求功能的堆叠，而是专注于维护一个稳定的基础，让生态可以在不牺牲简洁性的前提下持续演进。

---

# 🎯 设计原则

## ✨ 显式优于魔法

Kanketsu 更倾向于显式的 API，而非隐式的行为。

命令、选项和执行流程都直接在 Java 代码中声明。框架不进行任何运行时发现、隐式注册或自动装配。

这种方式让应用更易于导航、调试和重构。

**代码本身应该是唯一的真相来源。**

---

## 🧱 静态优于动态

Kanketsu 更倾向于静态结构，而非动态机制。

反射、运行时 classpath 扫描以及其他运行时发现技术，只要可行就刻意避免。

这一理念带来了：

* 可预测的运行时行为；
* 出色的 GraalVM Native Image 兼容性；
* 无需反射配置；
* 更快的启动速度和更低的运行时开销。

静态代码对开发者和编译器都更友好。

---

## 🧩 模块化优于单体

核心框架应保持专注。

Kanketsu 有意将核心 CLI 功能与可选的生态功能分离开来。框架不会不断膨胀核心，而是将额外功能以独立模块的形式实现。

这让核心保持：

* 轻量；
* 稳定；
* 易于维护；
* 易于采用。

某个功能不被包含，不是因为它不重要——而是因为它属于别的地方。

---

# 🏗 这些原则如何塑造 Kanketsu

设计原则贯穿于整个框架之中。

| 决策                          | 原则                  |
| ----------------------------- | --------------------- |
| 基于构建器的 API              | 显式优于魔法          |
| 不使用反射                    | 静态优于动态          |
| 不进行运行时扫描              | 静态优于动态          |
| 零传递依赖                    | 模块化优于单体        |
| 独立模块                      | 模块化优于单体        |

实现遵循原则——而非原则迁就实现。

---

# 📦 核心与生态

核心的职责是有意限定的。

**核心**模块专注于：

* 命令路由；
* 参数解析；
* 命令执行；
* 构建 CLI 应用所需的公共 API。

附加功能属于生态的范畴。

例如：

* 交互式 REPL；
* 日志集成；
* Spring 集成；
* YAML 或 JSON 配置；
* 注解处理；
* Shell 补全；
* 其他平台特定扩展。

将这些能力置于核心之外，让它们可以独立演进，而不会增加框架本身的复杂度。

---

# ⚖️ 权衡取舍

每个架构决策都涉及权衡。

Kanketsu 有意选择了：

* 显式配置而非自动发现；
* 模块化而非开箱即用的一站式便利；
* 长期可维护性而非功能堆积。

因此，应用可能需要比注解驱动框架多写一点点代码。

这不是局限——而是为了清晰性、可预测性和可维护性而做出的设计决策。

---

# 🏗 稳定的基础

Kanketsu 的目标不是成为一个大而全的 CLI 平台。

相反，它旨在提供一个**小巧、稳定、可预测**的基础，让丰富的生态模块可以在此基础上构建。

核心应该保持小巧。

生态应该保持自由生长。

每一个新功能都应当加强这些原则——而不是削弱它们。
